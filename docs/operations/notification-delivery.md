# Resend email and Hubtel SMS

School notifications can create external reminders through Resend and Hubtel. Announcements, assignments, fee reminders, messages and other existing in-app notification producers share the same PostgreSQL outbox trigger. This is school alert delivery, not bulk marketing or password-reset/OTP delivery. Messages contain a generic sign-in reminder; pupil names, message contents, grades and balances stay in the portal.

## Configure and enable

1. Apply `pnpm --filter @schoolhub/api migrate:deploy` before starting the new API. The migration creates delivery, consent, quota, suppression and provider-event tables and an atomic notification/outbox/job trigger. There is no historical backfill.
2. Rotate any API key shared in chat or other public channels. Put the replacement `RESEND_API_KEY` in your deployment secret manager, never source control. Set `RESEND_FROM_EMAIL=no-reply@notifications.drewstechservices.com`. Verify that sending domain in Resend and configure its required DNS records, including SPF/DKIM and your DMARC policy.
3. In Resend, add your public HTTPS endpoint `https://YOUR_API_HOST/api/webhooks/resend`. Subscribe to `email.sent`, `email.delivered`, `email.delivery_delayed`, `email.bounced`, `email.complained`, `email.failed` and `email.suppressed`. Store its signing secret as `RESEND_WEBHOOK_SECRET`. The exact raw body, Svix signature and timestamp are verified. Unsigned requests are rejected.
4. In Hubtel, obtain the live SMS credentials and approved alphanumeric sender ID (up to 11 characters). Set `HUBTEL_CLIENT_ID`, `HUBTEL_CLIENT_SECRET`, `HUBTEL_SENDER_ID`, and confirm your assigned `HUBTEL_SMS_BASE_URL` in the portal. The default is `https://smsc.hubtel.com/v1/messages`; only HTTPS Hubtel subdomains with that path are accepted. The integration uses Basic-authenticated JSON POST `/send` and GET `/{messageId}` status polling. If your account provides a different API contract, keep SMS disabled until its contract is verified. No unsigned SMS callback is trusted.
5. Set the correct public `WEB_ORIGIN` and `NOTIFICATION_DELIVERY_ENABLED=true` on the API. Restart it. It polls durable work every 30 seconds; replicas claim jobs using database leases. Providers with missing configuration do not block the other channel.
6. As school owner/admin, open **Notifications → School delivery controls**, enable the desired channel and enter a nonzero daily quota. Email and SMS are initially disabled with zero quotas. These are UTC-day reservation limits, not currency budgets. Each SMS is fixed ASCII and under 160 characters (one segment). Provider pricing and account balances are managed in their dashboards.
7. Each recipient explicitly opts in under **Email & SMS preferences** for that school. Email requires a verified account address. SMS requires a valid Ghana mobile number on their profile (`024…`, `23324…` or `+23324…` formats). SMS ownership is not OTP-verified by this feature. Correct the profile before opting in. Changing consent does not enqueue old notifications.
8. With consenting test accounts, publish a new school announcement and inspect delivery history plus the provider dashboard. Validate one successful email and SMS, one bounced address, consent withdrawal and a quota hit before wider enablement. No live delivery is performed by automated tests.

## Reliability and operator actions

- The in-app notification, eligible outbox rows and background jobs commit in one database transaction. Announcements now commit publication and their notification creation in that transaction too. Membership, school subscription, current contact, consent, suppression and quota are rechecked immediately before each send.
- A send has a 23-hour window from notification creation. Resend requests keep the same delivery ID/idempotency key and immutable payload; automatic exponential retries are capped by the durable job's five attempts. Resend retains keys for 24 hours, so expired work is never resent automatically. A crash after email submission can be recovered using the same key within the original window.
- Hubtel does not have a verified idempotent send contract in this integration. A rate-limit rejection can retry; timeout, server error, malformed success or a crash after submission becomes **UNKNOWN**, never a blind resend. Investigate in Hubtel first.
- **ACCEPTED** means the provider accepted a request. It is not delivery. Email delivery is confirmed by signed events; SMS delivery by authenticated polling. SMS status is polled every five minutes, for at most seven days; absence of a final receipt then becomes **UNKNOWN**. Delivered does not mean read.
- Webhook events are deduplicated and retained even when they arrive before the send response. Processing joins only events with known deliveries, so unmatched messages from another application on the same Resend account cannot starve real receipts. Late accepted/delayed events cannot downgrade delivered, bounced or complained states. Verified bounces/complaints suppress future email to the contact hash across schools.
- Owner/admin can select **Review email retry**, document a reason and replay an unaccepted **FAILED** or **DEAD** email within the original 23-hour window. The API retains its payload/key, rechecks eligibility, audits the action and rejects cross-school IDs, accepted messages, expired messages and SMS. Fix configuration first. Suppressed/unknown/expired deliveries are not replayable through this UI.
- Disable the global switch to stop worker submission and SMS polling, or disable a school's channel to stop that school's pending submissions. Webhook verification remains active to record outstanding email receipts. Existing in-app notifications keep working when external delivery is disabled.
- History is paginated and school-scoped; members see their own deliveries, owner/admin see school deliveries. Contact addresses, bodies, provider secrets and raw provider errors are excluded. Access to the database itself must be restricted: outbox contacts and prepared generic payloads contain personal contact data. Include these tables in backup, access and retention policies. Provider-event records contain only IDs, type and timestamps; signed but unmatched events may belong to another app using the same Resend account.
- No automatic deletion/unsuppression policy is applied: investigate suppressions before restoring contact eligibility. Retain audit evidence per the school's policy and implement a reviewed retention process before large-scale use.

## Validation

Provider tests use fake HTTP transports. PostgreSQL tests cover transactional rollback, real trigger/job insertion, membership/consent/contact withdrawal, immutable payloads, concurrent quota reservations, crash recovery, signed/replayed/early webhook events, suppression, expiry, replay audit and authorization. Full application E2E verifies exact raw-body signature handling through the production Better Auth parser. Desktop/mobile browser tests cover recipient preferences, school quotas, retry and role isolation.

Primary contracts: [Resend idempotency](https://resend.com/docs/dashboard/emails/idempotency-keys), [Resend webhook verification](https://resend.com/docs/webhooks/verify-webhooks-requests), [Hubtel developer portal](https://developers.hubtel.com/). Verify your Hubtel account endpoint in its dashboard; do not substitute credentials from another application.
