# Password recovery through Resend

Open **Forgot password?** on the sign-in page. A user with an existing verified email and credential account can request a reset without being signed in, including after an administrator-issued password expired. Unknown, unverified and banned accounts receive the same generic response. Accounts without a verified address need administrator-assisted credential reissue; this flow does not silently verify an address.

## Setup

Apply `pnpm --filter @schoolhub/api migrate:deploy`. Use the existing Resend configuration: fresh `RESEND_API_KEY`, `RESEND_FROM_EMAIL`, `RESEND_WEBHOOK_SECRET`, and `NOTIFICATION_DELIVERY_ENABLED=true`. Set the correct public `WEB_ORIGIN`, owned `TENANT_ROOT_DOMAINS`, and `BETTER_AUTH_SECRET` (at least 32 characters). No additional provider or encryption secret is needed. Credentials belong on the API, never in web build variables.

Security emails bypass school alert consent and school broadcast quotas. They require an explicit recovery request and a verified, non-banned account. Recovery remains available when the school's subscription is suspended so owners can regain access. Sending is globally disabled until Resend is configured. Missing configuration returns the same unavailable response for every email, without account lookup.

## Security and delivery behavior

- `/api/account/password-recovery/request` accepts an email and optional school slug; it uses a server-validated request Origin (or the configured web origin). It constructs a fixed `/reset-password` destination, not a caller-supplied redirect. `originPolicy` covers owned HTTPS tenant domains and configured development origins. Configure trusted proxy hops so IP throttles see the real client.
- Each request has a minimum 500ms response floor and queues email locally; provider latency never affects the public response. Unknown, unverified, banned, non-credential and rate-limited accounts receive identical success bodies. Endpoint throttles are ten requests per ten minutes per IP and five completion attempts per minute per IP per API instance. Eligible accounts also have a database-enforced three-request rolling hourly limit across replicas.
- Tokens contain 256 bits of randomness, expire after 15 minutes and are stored only as SHA-256 hashes. The encrypted outbox payload contains the mail recipient and link; AES-256-GCM uses an HKDF-derived key from `BETTER_AUTH_SECRET` with the request ID as authenticated context. Contact fingerprints are pseudonymous data, not anonymized records.
- Links put the token in a URL fragment. Browsers do not transmit fragments in HTTP requests. The reset page removes the fragment from browser history after reading it, and submits the token and password only in an HTTPS POST body. Never enable request-body logging for recovery endpoints or capture form values in analytics/session replay. A page refresh requires reopening the original email link. No reset token, password, recipient address or provider error body is written to job/audit logs.
- Request insertion, earlier-link revocation, encrypted mail insertion and job creation commit together. Only the most recent link works. Each link is also bound to a fingerprint of the existing credential; a normal password change or administrator reissue immediately invalidates older recovery links. A queued earlier email is suppressed when superseded; an email already in flight can still arrive, but its revoked token cannot reset anything. An unauthenticated request never consumes a currently valid password or creates a session.
- The worker polls every ten seconds and rechecks account/contact eligibility. It uses the existing leased jobs and five-attempt exponential backoff, preserving the exact Resend payload and idempotency key within the 15-minute token window. It stops attempting delivery when less than one minute remains. Payloads are erased on provider acceptance, revocation, consumption, expiry or terminal failure. Provider acceptance is not proof the email arrived; tell users to check spam and request a fresh link later if necessary. There is no manual replay of expired security email.
- Completion hashes the password before opening a transaction, then locks the user, rechecks the token/expiry/account/contact, writes the credential, clears temporary-password flags, revokes all sessions and trusted devices/pending 2FA challenges, consumes the token and records an audit in one transaction. Concurrent use succeeds once. A failed transaction leaves the token, password and sessions unchanged. Rejected weak passwords do not spend the token.
- TOTP enrollment, secret, backup codes and account lockout are preserved. Password reset never bypasses authenticator verification and never signs in automatically. Lost authenticators require backup codes or the existing administrator-assisted 2FA recovery process. SMS/email OTP is deliberately not enabled as a weaker alternate sign-in factor.
- Native Better Auth password-reset endpoints are disabled so there is no parallel path that skips these lifecycle and audit controls. Normal authenticated password change remains available.
- Hashed recovery/request metadata and completed jobs are retained for 24 hours, then cleaned in bounded batches; audit records retain the security event without bearer material. Payload expiry cleanup runs even when external delivery is switched off. Keep an API instance running for cleanup, and include these tables in encrypted backups and retention policies. Rotating `BETTER_AUTH_SECRET` makes queued payloads unreadable; after rotation users should request fresh links. Never restore expired links or manually extend their validity.

## Acceptance

Automated tests use fake provider transports only. CI covers real PostgreSQL transaction rollback, concurrent token consumption, rate limits, expiry/revocation/contact changes, immutable validity fields, encrypted payloads, full application recovery with real password/TOTP sign-in, session/challenge/trust revocation, and desktop/mobile UI journeys. After deployment, request a link for a consenting verified test account and verify actual delivery, single use, expiration, sign-in and 2FA before wider acceptance.
