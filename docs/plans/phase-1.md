# Phase 1 — Finance exports: Print, PDF and Excel only

## Goal

Remove every CSV export path from SchoolHub while preserving CSV import and template workflows. Standardise web exports, enforce finance/payroll export permissions, add server-rendered finance exports with export audit entries, and cover the contract with regression tests.

## Scope and implementation plan

1. **Create the phase plan before code changes.** Work on `feat/phase-1-finance-exports`, based on `main`. Do not alter `main` directly.
2. **Shared web export contract** (`apps/web/src/lib/table-export.ts`): add explicit column types (`text | number | money | date`), optional total rows and report metadata (school, period, filters, generated by/at). Keep text as text; numeric/money/date columns must be typed correctly in Excel. Freeze the header, apply `#,##0.00` to money, size columns safely, include formula-based totals where columns are aggregatable, and add a Report info sheet. Improve PDF headings, generated timestamp, page numbers, and Confidential footer for payroll. Keep print ink-friendly and include report metadata.
3. **Shared menus and portal replacements**: remove CSV options/documentation from `components/ui/data-table.tsx` and `components/school/workspace-ui.tsx`; remove `toCsv`/`downloadCsv` export helpers but retain CSV parser/template-import support. Replace direct CSV exports across accountant, finance reporting, expenses, inventory, payroll and admin audit pages with the shared Print/PDF/Excel exports; no CSV export remains in any portal.
4. **Permissions**: keep the existing table-export role gate, but provide a stricter policy for payroll/salary data (only `accountant`, `owner`, `headteacher`). Enforce this restriction in the UI and API, not merely by hiding a button.
5. **Server-side exports and audit**: implement school-scoped, role-checked endpoints for large finance reports and payroll Excel exports, plus server-rendered PDFs for receipts, invoices, statements and payslips where the current models/endpoints provide sufficient data. Each successful export writes an audit row with actor, export type, filters, and row count. Only add a public QR verification endpoint if its minimum-data response, rate limit, and verification semantics can be securely supported by existing models; otherwise explicitly document it as deferred.
6. **PDF library choice**: use `jspdf` and `jspdf-autotable`, already used by the web app, for Node-compatible generated PDFs. This avoids adding a second PDF layout engine and keeps layouts and table semantics consistent. Add API workspace dependencies and lockfile importer entries as required. Use the existing `qrcode` dependency only if adding a QR code to a server PDF can be done without exposing unnecessary student/payment data.
7. **Regression tests**: add tests ensuring export code cannot emit `text/csv`, Excel read-back validates numeric cell types and formula totals, report metadata exists, payroll export policy excludes admin/teacher/staff, and API export routes enforce roles/school scope and audit successful exports. Preserve and test CSV import parsing.
8. **Verification and gate**: run `pnpm typecheck`, `pnpm --filter @schoolhub/api lint`, `pnpm --filter @schoolhub/api test`, plus web typecheck/build and export-specific tests. Fix regressions, inspect the final diff and CI result, and report changed files, migration status, test results, assumptions, and deferred items. Stop for review; do not begin Phase 2.

## Safety and accounting constraints

- Every server export resolves the authenticated school from the request context; no client-supplied school ID may widen the scope.
- Payroll/salary output is confidential and excludes roles outside accountant, owner and headteacher, including through direct API requests.
- Export audits must avoid logging full salary, bank, or student PII in filter values. Log only the export type, permitted filters, actor, timestamp, and row count.
- Exports are read-only; do not change or delete financial records, and do not alter payment, invoice, payroll or audit history.
- Preserve CSV import support (including student import) and never expose money as floating-point calculations in server accounting logic. Export formatting may use Excel numeric cells for values already represented as database decimals.

## Known caveats to verify

- Existing list endpoints have previously had pagination/large-school correctness concerns. Export endpoints must query school-scoped records server-side and must not silently truncate at 500 rows.
- Public QR verification is optional in the approved prompt. If existing receipt references do not provide safe, unambiguous verification semantics, omit that endpoint and state why in the phase report.
- Do not introduce legal/accounting policy or tax values as part of export formatting.
