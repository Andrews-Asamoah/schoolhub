SchoolHub Desktop App: Offline-First Implementation Plan
Draft for review · 9 November 2026 · Based on dev at b1faa81
The desktop app is offline-first: it works fully with no internet, keeps its data in an encrypted local database, and pushes changes to the web when a connection exists. That makes sync the core of the product and raises the estimate from 7 to 9 weeks to about 23 to 27 weeks for one full-time developer, with a first signed online release around week 6.
Your schools' connections are usually slow and only occasionally good, so the design treats slow as the normal case: every screen works from the local database, and sync is small, resumable and never blocks a teacher. Desktop access is sold per school and tied to the school's subscription, and superadmin pages never ship in the desktop app. I read purely offline as offline-first, with the server staying the system of record for every school and device.
What the repo tells us
The API already has most of the safety features sync needs, but not a change feed, device records or an offline identity. These facts were checked in the code on dev at b1faa81.
• Auth. Better Auth with bearer() and twoFactor(). Tauri origins are allowed only outside production in origin-policy.ts. Requests with no Origin header are allowed but still pass auth, tenant and role guards.
• Marks. The writer returns a 409 ConflictException when another user changed the marks, and the web keeps the draft. Sheets can be locked, submitted, past a deadline, or covered by a per-teacher extension.
• Attendance. The batch endpoint already takes an idempotency-key header and rejects reuse for a different batch.
• Finance. Manual journals use idempotency keys, and a FinanceIntegrityJob runs daily. Money has the strictest controls in the system.
• Tombstones. Only 12 deletedAt columns exist, so most tables cannot tell a client that a row was removed.
• Reusable logic. Grading, totals, ranking and the stanine boundary functions are pure TypeScript (assessment-entry.ts and packages/shared), so the desktop app can run the same code as the server.
• Mobile precedent. apps/mobile stores the bearer token securely and has a logout tombstone, but does not support accounts that need a 2FA challenge, because the challenge cookie is not persisted.
• Browser assumptions in apps/web. Tenant from window.location, localStorage for drafts and theme, anchor downloads, and window.print.

Offline screens use the same HTTP-shaped calls as online ones, answered from a local database. A sync engine moves changes in the background.

Local database
• SQLCipher through rusqlite, WAL mode, one connection owned by Rust. The webview never opens the file; it calls three commands: db_query, db_exec, db_transaction.
• A random 256-bit key per database, held in the OS credential store (Windows Credential Manager, macOS Keychain, Secret Service).
• One file per school and user under the OS user's app data folder, so staff sharing a PC cannot read each other's data.
• Tables: replicated mirrors with a serverVersion column, outbox, sync_state (cursor, device id, lease), needs_attention, and an encrypted file cache.
• Forward-only numbered migrations, each in a transaction after an automatic backup. The app refuses to open a database newer than itself.
• Scale is small: a school is thousands of students and roughly 10^5 mark cells, well within SQLite.
Local API facade
• A route manifest maps method and path pattern to a handler. Unlisted routes go to the server when online and show a needs-internet state when offline, through one shared hook.
• Handlers return the same JSON as the API, validated by the same Zod schemas in packages/shared. Contract tests run identical fixtures against the real API and the facade, which is the control against drift.
• Local authorization is a convenience only. The server re-checks every pushed command.
Shared domain code
Any rule that decides a number or a lock moves from apps/api into packages/shared, with its tests: totals and ranking in assessment-entry.ts (the stanine boundary functions are already shared), effectiveDeadline, and attendance summaries. The server and the desktop then run one implementation. Derived values the desktop computes are marked provisional until the next pull replaces them with the server's.
Platform seam
Browser assumptions in apps/web (tenant from window.location, localStorage, anchor downloads, window.print) move behind lib/platform, which has a web and a desktop implementation chosen at build time. No @tauri-apps/* import is allowed outside lib/platform/desktop/ (an ESLint rule enforces it), and the web build must stay behaviour-neutral, proven by the existing tests and a bundle check.
Sync protocol
The desktop pulls changes it is allowed to see and pushes commands it recorded offline. The server applies commands by calling the existing domain services, so validation, authorization, locks and audit stay in one place.
1. Register a device. After an online sign-in the app calls POST /sync/devices and gets a device id. An administrator can revoke a device, and the server then rejects its pushes.
2. Pull. GET /sync/pull?cursor=… returns changes (upsert or delete, with a version) limited to the user's scope, plus a new cursor and the server time. The first sync, or a cursor older than the retention window, downloads a paged snapshot instead.
3. Record offline. Every offline write updates the local rows and appends a command to the outbox in one transaction: a UUIDv7 opId, a per-device sequence number, the command type, a payload, the version it was based on, and capturedAt.
4. Push. POST /sync/push sends commands in order. Each command is applied in its own transaction, so one failure never blocks the rest. The result per command is applied, duplicate, conflict (with the current server state) or rejected (with a code and message).
5. Settle. Applied and duplicate commands leave the outbox. Conflicts and rejections move to a Needs attention list. Nothing is ever dropped silently.
Design rules:
• Idempotent. A sync_operation ledger keyed by device and opId stores each result, so a retry after a dropped connection returns the same answer and never applies twice. Attendance already supports this pattern.
• Commit-safe cursor. A plain auto-increment can expose a later row before an earlier uncommitted one and make clients skip changes. The change log is written in the same transaction as the domain write, and the feed only exposes rows older than the oldest open transaction. A concurrency test must prove it.
• Commands, not row diffs. The desktop sends intent (record these marks, submit this sheet) rather than table rows, so server rules apply as they do online.
• Server-side scoping. The pull filters by role and assignments. A teacher never receives classes they do not teach.
• Triggers. Sync runs at launch, on reconnect, every minute or so with jittered back-off, on Sync now, and when the app closes if there is something to send. Connectivity is decided by a lightweight health request, not navigator.onLine.
• Versioned protocol. Commands carry a protocol version and the server converts older ones, for at least as long as the longest offline lease, so a laptop that was offline for weeks can still push after the API has been updated.
Slow connections
Because your schools' links are usually slow, these rules are part of the protocol, not tuning for later.
• Small on the wire. Commands carry only the changed cells, pull responses carry only changed fields, and every sync response is compressed (gzip or Brotli). Proposed starting targets, to confirm in Phase 0: a class register under 5 KB and a 40-pupil, 6-component marks sheet under 20 KB uncompressed.
• Resumable. Pull is paged and the cursor is saved after each page, so a dropped connection resumes where it stopped. The first snapshot can pause and resume. Push returns a result per command, so only unconfirmed commands are resent.
• Never blocks the screen. Every read and write is local. Sync runs in the background with a visible status, and a teacher can pause it.
• Pushes first. Unsent work goes before downloads. Large optional downloads, such as cached report PDFs, wait until the essentials are synced and can be cancelled.
• Patient and polite. Timeouts and back-off adapt to measured throughput, with one connection at a time and no fast polling. Configuration such as grading scales uses ETags, so unchanged data costs a few bytes.
• Tested on a bad link. Phase 0 and the hardening phase run every sync scenario on a throttled profile, for example 64 kbps, 1 second latency and 10% packet loss.
• Installing and updating. The updater downloads a full installer package (size to be measured in Phase 0), so schools can also install an update from an installer file copied by USB. An installer with the WebView2 runtime included avoids a second download on first install.
Conflicts, deadlines and clocks
The server decides every outcome, and the desktop never overwrites someone else's data silently. A command that cannot be applied goes to Needs attention with the reason and the current server value, and the teacher resolves it on screen.

Late arrivals are accepted. A command captured before the effective deadline (including any per-teacher extension) is applied however late it syncs, and the audit record notes that it arrived late. To prevent back-dating, the app derives capture time from the last server time it saw plus a monotonic counter, so changing the PC clock does not reopen a closed sheet, and the server rejects a command whose capturedAt is earlier than that device's previous sync. A lock or an earlier submission still wins: a deadline rule never overrides them.
Clocks. Client time is never an authority for ordering. The app records the server time at each sync, tracks the offset with a monotonic counter, and flags a device whose clock jumps backwards or far ahead. Ordering comes from the per-device sequence number and server-assigned versions. Attendance dates are the school's calendar day, not a timestamp.
Identity, security and data-loss protection
A laptop that can be offline for weeks holds students' data and may be shared, lost or stolen. The design trusts the device only for a bounded time and protects unsent work.
Offline identity
• First sign-in is online, including any 2FA challenge. The HTTP plugin keeps the short-lived challenge cookie in memory, which is a Phase 0 test item. If it fails, the API issues a bearer-friendly challenge token instead.
• Offline lease. The server returns a signed lease (user, school, roles, scope hash, expiry) verified in the app with an embedded public key, so editing local files cannot extend it. Every successful sync renews it. The lease is the shorter of 30 days and the end of the school's paid subscription period.
• Offline unlock uses the account password, checked against a local Argon2id verifier set during the online sign-in, plus the device-bound database key in the OS credential store. TOTP is not checked offline because the secret stays on the server.
• After the lease expires the app becomes read-only for existing data, allows Sync now and backup export, and blocks new edits until the user signs in online.
• Revocation (a removed teacher, a changed role, a lost device) takes effect at the next sync: the server rejects pushes from that user or device, and the app wipes its local database when it learns of it. The lease length is therefore the exposure window.
Security controls
• Capabilities follow least privilege: no shell plugin, opener limited to https:, HTTP scope pinned to the API origin, file access limited to user-chosen paths and the downloads folder.
• A strict Content-Security-Policy with connect-src limited to the API origin, no remote scripts and no unsafe-eval. Remote pages are never loaded into a window with IPC access.
• Devtools off in release builds, no shipped source maps, and pnpm audit, cargo audit and cargo deny in CI.
• No personal data in logs, diagnostics or crash reports. Every applied command is audited with its device id and capturedAt.
• The staff-only BECE rule is enforced in the facade and the sync scope, and has its own automated test, not only hidden navigation.
Protecting unsent work
• Lock, don't sign out. The default action locks the app. Signing out or removing a school from this computer is blocked while commands are pending, unless the user exports a backup and confirms.
• Always-visible sync status with a pending count. Closing the app with pending changes offers to sync first, and warns after a set number of days without a sync.
• Encrypted backup export. One file holding the outbox and the data needed to re-send it, encrypted with a passphrase the user chooses. It can be imported on another install of the same account, so a dead laptop does not mean lost marks.
• Crash safety. WAL mode with durable writes. The outbox is written in the same transaction as the data it describes, so a power cut cannot leave data without its command.
• Shared PCs. One database per user, an idle lock, and a short data-handling note for schools explaining what is stored on the machine.
Licensing and provisioning
Desktop access is sold per school, so entitlement is enforced by the server, never by the installer.
• Entitlement. A desktop flag in the plan's existing features data (SubscriptionPlan.features), with an optional per-school override in Subscription.settings. A superadmin switches it on in the existing Plans and Subscriptions pages on the web. There is no new billing mechanism.
• Server enforcement. Device registration, pull, push and lease renewal check the flag and the subscription through the same tenant guard that already blocks inactive schools. A school without the entitlement gets a clear message that desktop access is not enabled.
• Accounts. The superadmin creates the school and its owner and admin accounts on the web, as today. The desktop app has no sign-up and no school-creation screen. A new account's forced password change happens at its first sign-in, which is online.
• Superadmin is excluded in three layers. (1) Build: the /admin/* routes, the superadmin components and the public /apply route are left out of the desktop build, not just hidden. (2) Sign-in: a superAdmin account is refused on the desktop with a message to use the web portal. (3) API: sessions created by the desktop app are marked as such, and the super-admin module rejects them. Each layer has an automated test, plus a bundle check that no superadmin code is present.
• If a subscription lapses. The lease cannot renew, so after it expires the app becomes read-only. Commands already recorded still need to reach the server, so the push endpoint stays open for a grace period using the existing allow-inactive escape hatch, and backup export always works. The length of that grace period needs your decision.
• Device seats. Optional: a per-plan device limit, with an administrator screen to see and revoke devices.
• Downloads and updates. The installer link appears in the web portal only for entitled schools and uses a short-lived signed URL. The updater checks a manifest served by the API, so schools without the entitlement receive no updates. Confirm in the spike that the updater can send an authorization header.

Testing, CI/CD and distribution
Sync bugs lose data quietly, so testing weight moves from the screens to the protocol.
Testing
• Protocol tests on real PostgreSQL: duplicate pushes, out-of-order retries, a push cut off mid-batch, conflicts, locked sheets, revoked devices, expired leases, and the cursor under concurrent transactions.
• Property and chaos tests: random sequences of offline edits, kills, network flaps and clock jumps across two or three simulated devices, asserting that the final server state equals the expected state and nothing is applied twice.
• Contract tests: the same fixtures against the real API and the local facade, so the two cannot drift.
• Migration tests: every local database version upgrades to the latest, and an old pending outbox still pushes after an API update.
• Required checks: staff-only BECE rules, role and tenant headers, lock-not-sign-out with pending commands, and the update-required screen.
• End to end: extend the existing Playwright scripts against the desktop web build, plus a thin tauri-driver smoke test on Windows (install, launch, sign in, save a file). macOS has no WebDriver for its web view, so it relies on a manual release checklist.
CI/CD
• Each pull request: pnpm typecheck, web and API tests, cargo fmt --check, cargo clippy -D warnings, cargo test, dependency audits, and a check that the web build contains no Tauri code.
• Releases: tags desktop-vX.Y.Z run tauri-apps/tauri-action on Windows and macOS runners, sign the installers, and publish a draft release plus the updater manifest for manual approval.
• Updater: tauri-plugin-updater with minisign-signed artifacts, stable and beta channels, and the previous two releases kept available for rollback.
• Compatibility gate: the app sends its version, and the API answers 426 Upgrade Required below a configured minimum. Sync protocol versions stay supported for at least the lease length (see the sync protocol).
Distribution
• Per-user NSIS installer by default, so staff without admin rights can install it. An MSI for school IT, and an installer variant with the WebView2 runtime included for schools with poor connectivity (a much larger download).
• Code signing avoids SmartScreen warnings and affects adoption. Confirm which Windows signing options your legal entity and country can use, and start verification in Phase 1, because it can take weeks. macOS needs an Apple Developer account.
• Release files and manifests on GitHub Releases or R2, linked from a Download page in the web app. An About screen shows the version and a copy-diagnostics button with no personal data.
• When it ships, update ARCHITECTURE.md (diagram and the apps/desktop section) and the notes on production origins.

Decisions I need from you
